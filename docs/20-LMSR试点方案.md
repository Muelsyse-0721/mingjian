# LMSR 份额化试点方案

> 目的：让"平仓"成为可能。彩池数学上做不到（见 docs/19 第二节），必须先把定价换成份额制。
> 本方案只做**灰度试点**，不动存量彩池题。

## 一、模型

LMSR（Logarithmic Market Scoring Rule）：平台当自动做市商，按已售份额定价。

```
成本函数   C(q) = b · ln( Σ e^(q_i / b) )
即时价格   p_i  = e^(q_i / b) / Σ e^(q_j / b)      （Σp = 1）
买入 Δ 份  付 C(q + Δe_i) − C(q)
卖出 Δ 份  收 C(q) − C(q − Δe_i)
```

三个好性质：

1. **价格永远是概率**，加总恒为 1，不需要归一化
2. **平台最大亏损有闭式上界**：`b · ln(n)`，与交易量无关
3. **买卖对称**，卖出即反向操作，不需要对手盘

## 二、参数（用数字定，不拍脑袋）

实测（二元题，初始 50/50）：

| b | 买 20 份滑点 | 买 100 份滑点 | 买 300 份滑点 | 单题最大补贴 b·ln2 |
|---|---|---|---|---|
| 100 | +2.5pp | **+33.2pp** | +49.0pp | 69 分 |
| 300 | +1.7pp | +8.3pp | +23.1pp | 208 分 |
| **500** | **+1.0pp** | **+5.0pp** | +14.6pp | **347 分** |
| 1000 | +0.5pp | +2.5pp | +7.4pp | 693 分 |

**取 b = 500**：典型下注 20–100 分只滑 1–5pp，体验接近"按价成交"；单题最坏补贴 347 分，
在积分体系里可接受（当前初始彩池常见 1000 分）。

三选项及以上：`b·ln(n)`，n=3 时 549 分，仍然可控。

配套硬约束：

| 约束 | 值 | 理由 |
|---|---|---|
| 价格上下限 | 2% / 98% | 防止 1 分钱买 99 份，也防止价格卡死无人能接 |
| 单用户单题持仓上限 | 3000 份 | 防止一人吃掉整条曲线 |
| 补贴熔断 | 用量 ≥ 90% × b·ln(n) | 触发后只允许卖出，不允许买入 |
| 单笔最小 | 10 分 | 与现有 `min_bet` 一致 |

## 三、抽水

按成交额收，费率随概率变化：

```
fee = 成交额 × f × 4p(1−p)      f = 5%
```

| 概率 | 每 100 分成交抽水 | 等效费率 |
|---|---|---|
| 5% | 0.95 分 | 0.95% |
| 25% | 3.75 分 | 3.75% |
| 50% | **5.00 分** | **5.00%** |
| 95% | 0.95 分 | 0.95% |

中间价与现有 5% 抽水一致，极端价降到 1% 以下——既不改总体收入，又让"刷极端选项"变贵。

与 Polymarket 的 `C×f×p(1−p)` 同构：中间价抽得多，极端价几乎不抽。好处是**抑制"1% 概率刷量"**——
在彩池里刷极端选项几乎没有成本，这里会被价格滑点自然惩罚。

**费率必须比彩池低**：彩池是结算时单边抽一次，份额市场是每笔成交都抽（双边）。
f=5% 时一次往返要付 9.5%（实测：买 49.72 / 卖 45.01，净损 4.72），会让交易者望而却步。
因此份额市场默认 **f=2%（往返约 3.9%）**，与 Polymarket 的 ~2%/边 相当；
彩池保持 5% 不变。可通过站点设置 `lmsr_fee` 调整。

## 四、数据与代码接缝

> **实现时的一个改进**：`q` 不落库。
> 原本计划把 `q` 写回 `jp_questions.lmsr.q`，但题目表写权限收紧到站长，
> 普通用户买入时改不了。改成**由流水推导**：`q = q0 + Σ买入份额 − Σ卖出份额`，
> 和彩池"池子由流水推导"同一原则。好处是单一事实来源、无并发写冲突、可随时重算。


不新建表，扩展现有结构（保持账本同源）：

| 位置 | 改动 |
|---|---|
| `jp_questions.mode` | 新增取值 `'lmsr'`（现有 `pool` / `fixed` 不变） |
| `jp_questions.lmsr` | 新 jsonb 列：`{ "b": 500, "q0": {} }`（q0 只是初始偏移，平时为 0） |
| `jp_bets.shares` | 新列：成交份额，**恒为正数**；买卖方向由 `kind` 决定 |
| `jp_bets.price` | 新列：成交均价 |
| `jp_bets.kind` | 新增 `'buy'` / `'sell'` / `'settle'`（彩池仍用 `'bet'`，互不干扰） |

**符号约定**（踩过的坑）：卖出流水里 `stake` 为负（现金流入），但 `shares` 存正数。
一开始把 shares 也存成负数，导致推导出 `q` 反向、持仓翻倍——现在所有读取处统一取 `Math.abs`。

**抽水**：买入时实付 = 成交额 + 抽水；卖出时回收 = 卖出额 − 抽水。
抽水不再单独记一行（避免多一种流水类型），成本与回收里已含。

**净资产口径保持不变**：`现金 + 在押 − 负债`，其中在押按**持仓成本**计（不按浮盈）。
理由：按市价计会让排行榜随价格抖动，也给"低买高卖刷净资产"开口子。浮盈只在持仓面板展示。

**破产保护不变**：净资产跌破 `force_min_net` 照样核销借款。买入时校验可用现金，不引入保证金。

## 五、结算

赢家：`份额 × 1 分`；输家：0。
已付成本已在买入时扣除，所以净盈亏 = 派彩 − 成本，直接体现在现金上。

派彩总量上限 = 持仓总份额 ≤ 平台收到的现金 + 补贴，而补贴有 `b·ln(n)` 上界，
**不会出现派彩超发**（彩池里靠池子守恒，这里靠闭式上界）。

## 六、老题怎么办

**试点期不迁移。** 存量题继续走彩池，直到自然结算完。

若将来要迁移，反解公式（softmax 平移不变）：

```
q_i = b · ln(p_i)          p_i = 当前池占比
```

代价：迁移瞬间"在押"要从彩池的"份额"换算成 LMSR 的"持仓"，历史流水会与实际持仓不一致。
所以更稳的做法是**新题新规则，老题老规则**，用 `mode` 分流，永远不迁移。

## 七、回滚

试点题**单独建、单独标记**，出问题只需两步：

1. 后台把该题 `lmsr.locked = true`，禁止新买入（只允许卖出）
2. 严重情况下按当前价格强制赎回全部持仓，题目转 `settled` 并附说明

不影响任何彩池题，也不改全局开关。

## 十、实测输出（用真实模块跑的，非估算）

`node tools/lmsr-sim.js 500`：

```
b=500  平台单题敞口上限 b·ln2 = 346.6 分

  份额    花费     均价   买后价格    滑点     抽水
    20     10.1  0.505     51.0%    1.0pp   0.50
    50     25.6  0.512     52.5%    2.5pp   1.28
   100     52.5  0.525     55.0%    5.0pp   2.62
   300    172.2  0.574     64.6%   14.6pp   8.42

买卖往返：买 100 + 100 + 200 份共投入 209.9，全部卖出收回 209.9，差额 0.0000
```

**往返差额为 0** 说明定价自洽：没有套利空间，卖出就是真实的平仓，而不是"退本金"。
这正是彩池做不到的那件事。

## 十一、先做哪一块

建议单独一轮做，并先补"净资产守恒"的回归测试。

## 十二、部署注意（踩过的坑）

**给表加列后必须刷新 PostgREST 的 schema 缓存**：

```sql
NOTIFY pgrst, 'reload schema';
```

否则接口层仍按旧表结构解析列名：读取可能看不出问题（`select *` 返回旧列），
但**写入带新列会直接失败**，报 `column ... does not exist`。

2026-10-22 的「点买入没反应」就是它——当天给 `jp_bets` 加了 `shares` / `price`，
忘了刷新缓存。

同时补了三处前端兜底，避免同类问题再表现为「静默失效」：

1. `state.busy` 为真时弹提示，而不是静默 `return`
2. `setBusy(true)` 与业务调用一起包 try —— 同步异常会把 busy 永远卡在 true，之后所有点击全部失效
3. 全局监听 `error` / `unhandledrejection`，错误写进界面而不是只进控制台
