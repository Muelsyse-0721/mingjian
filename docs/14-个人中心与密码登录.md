## 一、一句话结论

**密码只能在「新号注册」时设置；历史上用验证码注册的老账号无法补设密码。**
这不是产品取舍，是 SDK 契约的硬限制（见第二节）。个人中心必须如实提示，不得提供「给老账号设置密码」的按钮。

## 二、为什么老账号不能补设密码

| 事实 | 出处 |
|---|---|
| `signUp` 必须带 `verificationToken`，provider 拒绝「仅用户名 + 密码」的注册 | `app/test/vendor/wbcloud.js` → `AuthModule.signUp` |
| `verificationToken` 只在 `verifyOtp` 内部流转，**不返回给调用方** | 同上 → `verifyOtp` |
| 没有通用的 `updateUser({ password })` | 同上，AuthModule 无此方法 |
| `resetPasswordForEmail` 只接受 email；本项目账号是手机号 | 同上 |
| `resetPasswordForOld({ oldPassword, newPassword })` 需要**旧密码**才放行（sudo 校验） | 同上 → `resetPasswordForOld` |

结论链：设密码必须走 `signUp` → `signUp` 必须在新号分支 → 老号进的是 `signIn` 分支 → 老号没有任何可用的补设入口。

唯一可用的实现路径：把密码交给 `verifyOtp({ ..., password })`，由 SDK 在「新用户」分支内部拼进 `signUp`。`app/js/auth.js#signUpWithPassword` 就是这么做的。

### 参数名坑（已踩）

`signInWithPassword` / `signUp` 的入参只读 `{ phone }` 或 `{ email }`，**不读 `{ username }`**：

```
signInWithPassword({ username: '138...', password: 'x' })
→ error: "signInWithPassword requires exactly one of email or phone"
signInWithPassword({ phone: '138...', password: 'x' })   ← 正确
```

实现里统一只用 `phone`，并有单测断言「SDK 未收到 username 参数」。

## 四、auth.js 新接口

```js
// 手机号 + 密码登录：只校验长度 6-64（存量密码未必符合当前组合策略）
Auth.signInWithPassword('13800138000', 'abc123')
// → { ok:true, data:{user} } | { ok:false, error:{message:'手机号或密码错误'} }

// 新号注册并设密码：注册侧要求 6-64 位且字母+数字混合
Auth.signUpWithPassword('13800138000', 'abc123', '123456')
// → { ok:true, passwordSet:true }
// → { ok:true, passwordSet:false, reason:'exists' }   // 服务端已有此号，已回退验证码登录
// → { ok:false, error:{message} }

Auth.canSetPassword()
// → { allowed, state, reason }
//   state: pending-signup | set | unknown | anonymous
```

要点：

- `signUpWithPassword` 复用 `sendCode` 留下的内存 `pending`（含 `verificationId`）。`pending` **不落 localStorage**，验证码不打日志。
- 老号分支：`pending.isExistingUser === true` 直接走验证码登录；若预检说是新号但服务端报「已存在」，同样回退，返回 `passwordSet:false`，不报错——用户至少能登录成功。
- 错误一律翻译成中文，原始 provider 报文不回显。
- `canSetPassword` 只服务 UI 提示，**不作授权判断**；鉴权始终在 provider。

## 五、ProfileCore 口径

`profileStats(data, uid, opts)` 返回 `{bets, winRate, netWorth, openStake, debt, evidence, debates}`，逐条对齐 `app/js/loans.js`：

| 字段 | 公式 |
|---|---|
| 现金 | `opening_bonus + Σ(投注盈亏) + Σ借款本金 − Σ已还款`（`cashOf`） |
| `openStake` | `status='open'` 的质押合计（`openStakeOf`） |
| `debt` | `status='open'` 借款的「未还本金 + 未付利息 + 未付罚息」（`debtOf`/`outstandingOf`） |
| `netWorth` | `现金 + openStake − debt`（`netWorthOf`，天梯榜排序口径） |
| `winRate` | `round(胜 / (胜+负) * 100)`，无结算局为 0 |
| `bets` | 仅 `kind` 为 `bet`/缺省的投注笔数，奖励行（`kind='bonus'/'adjust'`）不计 |
| `evidence` / `debates` | 本人行数；`jp_debates` 拥有者列是 `creator_uid`，两种列名都认 |

> 注意：这三条公式在 `profile.js` 里重写了一份（为保持零依赖）。**改 `loans.js` 的资产口径时必须同步改这里**，否则个人中心与天梯榜对不上。

其他纯函数：

- `validatePassword(pw)` → `{ok, reason, strength:0-4}`；拒绝纯数字/纯字母，`strength` 只驱动进度条，不参与放行。
- `maskPhone('13800138000')` → `'138****8000'`；非法输入返回 `''`（调用方据此隐藏整行）。
- `composeProfilePatch({nickname, bio})` → 只含白名单键；nickname 2-12 字超界**丢弃该键**（不写坏数据也不清空原值），bio 截断到 80 字，空 bio 保留以便清空简介。
- `accountBadges(profile, ctx)` → `['站长','已设密码']` 之类；`ctx` 覆盖档案字段；昵称为空时追加 `'新用户'`。
- `composePasswordHint(passwordSet)` → 已设密码 / 未设密码（含「老账号无法补设」）两套文案。

## 六、SQL 判断依据

- `02-rls-tighten.sql` 对 `jp_profiles` 授予的是**表级** `SELECT, INSERT, UPDATE, DELETE TO authenticated`。PostgreSQL 表级 GRANT 不按列快照，新增列自动纳入，**因此不写列级 GRANT**。
- 行级策略 `uid = auth.uid()::text` 与列无关，新增三列自动落在「本人可读写、他人不可见」范围内。
- `password_set` 只是展示标记：本表不存密码/哈希/盐，真实凭据在 provider。被篡改最坏结果是徽标显示错误，不影响鉴权。
- 文末附了「线上若被改成列级授权、报 42501」的补救语句（默认不执行）。

## 修正（2026-10-19 12:5x）：老账号可设密码，忘记密码也能找回

前面「老账号无法补设、无找回」的结论**已作废**。继续挖 SDK 后发现两条被漏掉的通道：

1. `cloud.auth.resetPasswordForOld({oldPassword, newPassword})` —— 已登录且**知道旧密码**时的改密：
   `POST /v1/user/sudo {password}` → `sudo_token` → `PATCH /v1/user/password {sudo_token, new_password}`。
2. `cloud.auth.request` 是**公开方法**，可直接打底层端点；实测 `POST /v1/reset` **接受 `phone_number`**：

```
POST /v1/verification        {phone_number:"+86 138...", usage:"PASSWORD_RESET", target:"USER"} → verification_id
POST /v1/verification/verify {verification_id, verification_code}                              → verification_token
POST /v1/reset               {phone_number:"+86 138...", new_password, verification_token}     → 设置成功
```

- 手机号格式必须是 E.164：`+86 13800138000`（带空格），否则 400（正则 `^\+[1-9][0-9]{0,3}\s[0-9]{4,20}$`）。
- 这条链**不依赖旧密码、也不需要邮箱**，因此同时覆盖两种场景：
  - 老账号首次设置密码；
  - 已设密码但忘记 → 直接重置。

落地：
- `auth.js` 新增 `sendResetCode(phone)`、`resetPasswordWithPhone(phone, code, newPassword, verificationId)`、`toE164(phone)`；`canSetPassword()` 现在对已登录账号一律 `allowed:true`（未设=可设，已设=可重置）。
- 登录弹窗「密码」区新增链接「用短信验证设置 / 重置密码」，展开验证码 + 新密码 + 确认；个人中心卡片也加了「设置 / 重置登录密码」入口。
- 文案与测试同步修正（`composePasswordHint(false)` 不再说"无法补设"）。

未真机验证的部分：真实短信送达与 `/v1/reset` 的成功返回（需要你的手机号点一次）。失败路径（手机号格式、验证码错误、频率限制）已按服务端错误码翻译成中文。
